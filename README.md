# 🌱 PlantAí

> *Planta aí* — or *Plant AI*.

PlantAí is a neighborhood plant app: snap a photo to identify a plant, get AI-generated care tips, and give away seedlings (*mudas*) to people nearby.

The route to the MVP is charted as a [Wayfinder map](../../issues?q=label%3Awayfinder%3Amap) in this repo's issues.

## Stack
- **App:** Flutter
- **API:** NestJS + PostgreSQL/PostGIS
- **AI:** plant identification by photo + care tips generated by Claude

## Development setup
Run `npm install` at the repo root once. It enables the pre-commit hook, which formats and lints only the staged files in `api/` and `app/`.

The Claude Code `git-guardrails` hook needs `jq`; without it, every shell command is blocked. Its tests run with `.claude/hooks/block-dangerous-git.test.sh`.

## Running the API locally
Needs Node 24 and Docker. From `api/`:

```sh
npm install
cp .env.example .env   # then fill in the values; the API refuses to start if one is invalid
npm run db:up          # PostGIS and the S3 emulator in Docker (compose.yaml), waits until both are healthy
npm run db:migrate     # applies the Drizzle migrations in drizzle/
npm run catalog:load   # loads the Catalog seed: species, names and reference photos
npm run start:dev      # http://localhost:3000, with reload on change
curl localhost:3000/v1/health
```

`npm run db:down` stops the database and the emulator and keeps their data (each has its own volume). After changing `src/database/schema.ts`, `npm run db:generate` writes the next migration to `drizzle/`; review the SQL in the PR.

**Google Sign-In:** `scripts/google-oauth-wizard.sh` walks through recreating the Google Cloud project, the consent screen and the OAuth clients (two Android, one Web) from scratch, reading both SHA-1s with `keytool`, and writes `GOOGLE_WEB_CLIENT_ID` to `api/.env`. The Web client secret is never stored.

### Photo storage (S3 emulator)
Photos live in a private S3 bucket and are only served through presigned GET URLs valid for 1 hour (ADR 0007). Locally, `compose.yaml` runs an S3 emulator on `localhost:9000` and creates the `plantai-photos` bucket when it starts; `.env.example` already points at it. The code is the same as for AWS (`@aws-sdk/client-s3`, `S3_ENDPOINT` with path-style URLs), so phase 2 only changes `.env`: drop `S3_ENDPOINT` and the keys, and the Lambda role gives the credentials. Presigned URLs are signed for `http://localhost:9000`, which the phone reaches through `npm run dev:phone` (it also forwards port 9000); over Wi-Fi the photos do not open.

**Why RustFS (`rustfs/rustfs:1.0.4`):** it is the emulator that meets the requirements: presigned GET URLs with SigV4, `PutObjectTagging`/`DeleteObjectTagging` (the `unattached` tag), a pinned stable release and active maintenance (Apache 2.0; 1.0.4 came out in October 2026). It also checks signatures, so the bucket is private as on S3: a URL without signature gets `403`. MinIO no longer publishes its community images. Adobe S3Mock does not check signatures, so it cannot show that the bucket is private. Garage has no object tagging. LocalStack's image now needs an account token. The image is the same in `compose.yaml` and in `test/support/s3.ts`, where `test/s3-photo-storage.spec.ts` runs the real adapter against it with Testcontainers. The lifecycle rule that deletes `unattached` photos after 1 day is not emulated; it belongs to the phase 2 infrastructure.

The `PhotoStorage` port (`src/photo-storage/`) is what the rest of the API uses; tests swap it for `FakePhotoStorage` (`createTestApp(env, { photoStorage })`), which keeps the objects and their tags in memory.

### Catalog
The Catalog (species, names, reference photos) lives in the database. `npm run catalog:load` loads `catalog/catalog-seed.json` (built by `npm run catalog:build`; see `docs/spec/modelo-de-dados-e-api.md`, "Semente do Catálogo"): it upserts each species by `gbifKey`, syncs its names, downloads its Wikimedia photo (with an identifying `User-Agent`), shrinks it to 1200 px and stores it without the `unattached` tag. It mounts only the modules it needs (`CatalogLoadModule`), not the HTTP server, and ends with a summary of species, photos copied and failures. Running it again duplicates nothing and only retries what failed; until its photo is copied, a species shows the Wikimedia one by URL. `-- --seed <file>` loads another seed file.

GBIF name resolution (`species/match`) is the `GbifNames` port (`src/gbif/`), used by the API and by `catalog:build`; tests swap it for `FakeGbifNames` (`createTestApp(env, { gbifNames })`).

### Authentication
Every route requires `Authorization: Bearer <access token>` (a 15-minute JWT signed with `JWT_SECRET`); without a valid one it answers `401 UNAUTHENTICATED`. The pieces live in `api/src/auth/`:
- `@Public()` on a route or controller lets it through without a token (`/health` and the `/auth` routes use it). `/docs` sits outside Nest's router and is always public.
- `@CurrentUser() user: AuthenticatedUser` gives the controller the signed-in User (`{ id }`).
- Each way in has its own folder (`auth/signup/`), and all of them end in `Sessions.start(user)`, which answers `{ accessToken, refreshToken, user }`.
- `POST /auth/refresh` (`auth/refresh/`) rotates the refresh token: the one sent is revoked and a new pair of the same family comes back. A revoked token sent again revokes the whole family (`Sessions.revokeFamily`). The app's `ApiClient` calls it by itself on a `401 UNAUTHENTICATED`.
- `POST /auth/google` (`auth/google/`) checks the app's ID token through the `GoogleTokenVerifier` port (`google-auth-library`, audience `GOOGLE_WEB_CLIENT_ID`) and joins an existing account only as ADR 0001 allows. Tests swap the port for `FakeGoogleVerifier` (`createTestApp(env, { googleVerifier })`).
- Rate limits (`auth/rate-limits.ts`, `@nestjs/throttler` in memory) cover every `/auth` route through a global guard: 20 requests per minute per IP, plus 5 per 15 minutes per e-mail of the body (3 on the routes that send an e-mail, marked `@LimitsEmailsSent()`). Over the limit: `429 TOO_MANY_REQUESTS`; list it in the route's `@ApiProblems`. Tests run without limits unless they pass `createTestApp(env, { realRateLimits: true })` (`test/auth-rate-limits.spec.ts`).
- The request logger never logs bodies, and redacts `Authorization`.

Without `RESEND_API_KEY`, e-mails are not sent: the API log shows them, sign-up code included. With the key and `EMAIL_FROM=onboarding@resend.dev`, Resend delivers in test mode, only to the e-mail of the Resend account.

### API contract (OpenAPI)
`http://localhost:3000/docs` shows the Swagger UI, and `/docs/openapi.json` the document, generated from the routes' Zod schemas by `nestjs-zod`. Both are public. The document is versioned in `api/openapi.json`, and `test/openapi.spec.ts` fails when the generated one differs, so every contract change shows up in the PR diff.

To document a route:
- Response: a `createZodDto` class, named as the schema should appear (no `Dto` suffix, no `.meta({ id })`, which breaks `cleanupOpenApiDoc`), used with `@ZodResponse({ status, type })`. The global serializer parses the return value with it, so the docs cannot drift from what the route sends.
- Body or query: a `createZodDto` class as the parameter type; the global pipe validates it.
- Errors: `@ApiProblems('CODE_A', 'CODE_B')` with the route's own codes. It adds the shared ones (`VALIDATION_FAILED`, `APP_UPDATE_REQUIRED`, `INTERNAL_ERROR`) and the `X-App-Version` header. A protected route also lists `UNAUTHENTICATED`, and its controller takes `@ApiBearerAuth()`.
- A nullable primitive needs some metadata on the inner schema (`z.string().meta({ example }).nullable()`); a bare `z.string().nullable()` comes out as an array.

Then run `npm run openapi:update` (from `api/`) and commit `api/openapi.json` with the change.

Checks, the same ones CI runs: `npm run format:check`, `npm run lint`, `npm run typecheck` and `npm test`. The tests start their own PostGIS (and, for the storage adapter, S3 emulator) with Testcontainers, so Docker must be running; they do not touch the services from `compose.yaml`.

## Running the app on a phone
Needs Flutter 3.47 (Dart 3.13), the Android SDK and JDK 17, plus the API running on the notebook (above). From `app/`:

```sh
flutter pub get
```

The app reads the API address from `--dart-define=API_BASE_URL`; release builds have no default (debug builds fall back to `http://localhost:3000`). Pick one of two ways to reach the notebook:

- **USB cable:** forward the phone's ports 3000 (API) and 9000 (S3 emulator, for the photos) to the notebook and use `localhost`. `npm run dev:phone` at the repo root does it for you: it runs the API, re-applies `adb reverse` of both ports on every reconnect and tees the API log (e-mail codes included) to `api/logs/dev.log`.
  ```sh
  adb reverse tcp:3000 tcp:3000 && adb reverse tcp:9000 tcp:9000   # after every reconnect, unless dev:phone runs
  flutter build apk --release --dart-define=API_BASE_URL=http://localhost:3000 \
    --dart-define=GOOGLE_SERVER_CLIENT_ID=431388587561-jhgntmp6i18htkblrnopm61b0h3815ld.apps.googleusercontent.com
  ```
- **Wi-Fi:** phone and notebook on the same network; use the notebook's IP (`hostname -I`).
  ```sh
  flutter build apk --release --dart-define=API_BASE_URL=http://192.168.0.10:3000 \
    --dart-define=GOOGLE_SERVER_CLIENT_ID=431388587561-jhgntmp6i18htkblrnopm61b0h3815ld.apps.googleusercontent.com
  ```

**Google Sign-In** needs `--dart-define=GOOGLE_SERVER_CLIENT_ID=<Web client ID>`, the same ID as the API's `GOOGLE_WEB_CLIENT_ID`: Google issues the ID token for it, and the API checks it as the audience. PlantAí's is `431388587561-jhgntmp6i18htkblrnopm61b0h3815ld.apps.googleusercontent.com` (Google Cloud project `plantai-513101`); a client ID is public, not a secret. Without it the app still runs, and only "Entrar com Google" fails, with a message. The Android OAuth clients match the app by package (`dev.angelobez.plantai`) and the SHA-1 of the signing key, so Google Sign-In works only in APKs signed with the release key or with `~/.android/debug.keystore`, the two registered SHA-1s. Configuration errors show up in `flutter logs` as `Google Sign-In failed: ...`.

Then install with `adb install -r build/app/outputs/flutter-apk/app-release.apk` (or use `flutter run --release --dart-define=...` instead of building). Without a session the app opens on Login; "Entrar com Google" signs in with the account chosen on the phone, "Entrar com e-mail" signs in with e-mail and password or, through "Criar conta", creates the account; without `RESEND_API_KEY` the 6-digit code shows up in the API log. With a session (kept in `flutter_secure_storage` between runs) it opens on the Por perto tab. If the API refuses its version (`426`), it shows "Atualize o PlantAí" instead.

Plain HTTP is allowed only to `localhost`, `127.0.0.1`, `10.0.2.2` (emulator) and, when `API_BASE_URL` is a private IPv4 address (10/8, 172.16/12, 192.168/16), that address; the build generates the network security config from it. Change the Wi-Fi IP and you must rebuild.

**Release signing:** create `android/key.properties` (never committed) pointing at the upload key in `~/.config/plantai/`:

```properties
storeFile=/home/<you>/.config/plantai/upload-keystore.jks
storePassword=...
keyAlias=upload
keyPassword=...
```

Without it (as in CI) the release build is signed with the debug key, which cannot install over a phone that has the release-signed app.

Checks, the same ones CI runs: `dart format --set-exit-if-changed .`, `flutter analyze` and `flutter test`. After changing a `@JsonSerializable` model, regenerate its `.g.dart` with `dart run build_runner build` and commit it.

## CI
One GitHub Actions workflow (`.github/workflows/ci.yml`) runs on every pull request and on every push to `main`:

| Job | Runs when | What it does |
| --- | --- | --- |
| Detect changed folders | always | Lists the changed files and decides which parts run |
| API | `api/` changed | `npm ci`, `format:check`, `lint`, `typecheck`, `test` (Testcontainers on the runner's Docker), Node 24 |
| App | `app/` changed | `flutter pub get`, `dart format --set-exit-if-changed .`, `flutter analyze`, `flutter test`, Flutter 3.47.7 |
| `ci` | always | Fails if any job that ran failed or was cancelled; skipped jobs are fine |

Changing the workflow itself runs both parts. A docs-only PR runs neither, and `ci` still goes green.

`ci` is the only required status check on `main`, so the folder filter never leaves a PR waiting for a check that will not run. The protection (PR required, `ci` required and up to date with `main`, zero approvals, enforced for admins, no force pushes or deletions) is applied once with:

```sh
scripts/protect-main.sh            # current repo, needs gh with admin rights
scripts/protect-main.sh owner/repo # or an explicit one
```

It is already applied to this repository (2026-10-29). Run it again only to restore the rules. Since they bind admins too, nothing reaches `main` by direct push: docs, research and `/rodada` changes also go through a branch and a PR.
